1. 四层地图：这个项目由谁组成？

① 浏览器前端展示状态、接收点击、调用 API
static/
② FastAPI 后端接请求、执行规则、编排任务
app/
③ SQLite 数据库让新闻和任务状态在重启后仍存在
data/*.db
④ 外部服务RSS 站点、GPT 网页读取、DeepSeek 分析

“层”不是某种神秘技术，只是职责分工。浏览器负责交互，后端负责规则，数据库负责长期记忆，外部服务提供项目自身没有的数据或能力。

把代码词翻译成人话

  • 文件：一个有明确职责的工作间
  • 函数：可以反复执行的动作
  • 类：一种机器的设计图
  • 对象：正在工作的那台具体机器

把系统词翻译成人话

  • API 路由：后端对外的服务窗口
  • JSON：窗口交接的数据单
  • 数据库：不会随进程关闭而忘记的账本
  • 后台任务：接单后慢慢完成的耗时工作

2. 先追一条最短路径：页面读取状态

页面需要知道采集和 AI 分析是否正在运行。前端在 static/app.js 发出请求：

const data = await api("/api/status");
$("metric-articles").textContent = data.article_count;

可以先把它读成：“去后端的 /api/status 窗口拿一份状态，再把文章数量画到页面上。”

后端在 app/main.py 找到同名窗口。真实代码会比下面多一些字段，但结构就是：

@app.get("/api/status")
def get_status():
    return {
        "running": manager.running_run_id is not None,
        "article_count": database.article_count(),
    }

@app.get(...) 把 URL 和函数绑定起来。浏览器发 GET 请求时，FastAPI 调用函数，再把 Python 字典自动转换成 JSON 响应。

用户打开页面JavaScript 准备刷新状态
GET /api/statusHTTP 请求进入 FastAPI
读取当前状态后端汇总任务与数据库信息
渲染 JSON浏览器更新文字和数字

即时检查：用户刷新状态时，正确顺序是？

3. 再看完整业务路径：从关键词到情报

这个项目不是“抓到标题就结束”。它先收集候选新闻，再读正文、判断真相关、分析业务影响，最后生成日报。

  1. 构造查询：app/query_builder.py 根据关键词语言生成合适的 RSS 查询。
  2. 采集候选：app/collector.py 读取 RSS、解析 XML、初步匹配并去重。
  3. 保存事实：app/database.py 把候选文章和任务状态写入 SQLite。
  4. 读取正文：app/llm.py 中的 GPT 客户端用网页搜索读取链接内容，并保存正文、最终地址和内容哈希。
  5. 判断相关：app/intelligence.py 编排 DeepSeek，先判断是否真相关，再做业务分析。
  6. 呈现进度：static/app.js 周期性请求状态，使运行中的结果自动出现在页面。
为什么先存候选文章，再调用 AI？网络和模型都可能超时或限流。先保存候选，失败后才能知道“哪篇做到哪一步”，并继续重试，而不是从 RSS 重新开始。

4. 出错时，用“哪一层”缩小范围

页面不更新

先查浏览器请求和 static/app.js 的轮询，再看 /api/status 是否返回新状态。

接口返回 500

从 app/main.py 对应路由进入，沿调用链看后端日志和异常。

重启后数据消失

查写入数据库的路径、事务是否提交，以及应用实际连接的是哪个数据库文件。

出现 HTTP 429

这是外部服务层的限流信号；检查并发、重试间隔、配额和接口能力，不要只刷新页面。
