理解为什么 AI 分析要拆成三道关卡

你将追踪正文读取、相关性门控、业务分析和日报，并判断 429、暂停和失败属于哪个状态。

1. 三道关卡，而不是一次全做

读取正文GPT 网页搜索获得证据
相关性审核DeepSeek 判断是否真相关
业务分析仅分析通过阈值的文章
生成日报汇总指定日期与分类

如果一次请求同时判断相关性、写摘要、评风险，无关文章也容易生成看似合理的分析。先门控能减少噪声和模型成本。

2. 状态机让耗时任务可观察

pending → processing → success
                    ↘ failed
                    ↘ ignored

状态机不是某个库，而是“只允许数据按明确状态转移”的设计。正文、相关性和业务分析分别有自己的状态，所以页面能指出卡在哪一步。

3. Repository 与 Manager 分工

IntelligenceRepository

负责查询候选、保存正文、保存审核、记录失败和统计状态。

ArticleAnalysisManager

负责编排顺序、批次、暂停、复用、模型调用和异常决策。

一个负责“记账”，一个负责“流程”。这种分离让 SQL 和业务状态不会全部挤在同一个函数里。

4. 相关性门控

review = RelevanceAssessment.model_validate(result.data)

if review.relevance_score < threshold:
    review.is_relevant = False

if not review.is_relevant:
    continue

模型输出先由 Pydantic 校验，再应用系统阈值。只有真相关文章继续发生第二次 DeepSeek 调用。

5. 429 为什么要暂停整个批次？

429 表示提供方正在限流。继续快速处理剩余文章只会制造更多失败。因此网页读取遇到 openai_http_429 时：

  • 当前文章记录失败原因。
  • 当前批次停止继续调用。
  • 未开始文章保留为待处理。
  • 用户稍后可以重试，而不是重新采集。

可重试网络错误与永久错误要分开。例如未配置密钥没有必要自动重试，超时和 429 通常可以稍后重试。

6. 暂停不是强行杀线程

用户请求暂停时设置一个事件标记。当前文章处理完成后，循环检查标记并停止。这样不会在写数据库一半时突然中断。
